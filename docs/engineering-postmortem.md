# 我的项目测试全绿，但用户装不上它

> 两天里我给一个命令行工具修了 5 个 bug。
> 它们有个共同点：**每一个都能让"测试通过"和"产品是坏的"同时成立。**
> 而其中一个，是**一键安装必然失败**。

## 先交代背景

`mcd-valor`，一个查麦当劳积分和优惠券的命令行工具，11 个命令，2005 行，零第三方依赖。

开发时我按惯例写测试。写完跑一遍，绿一片，心里挺踏实。

然后我开始做一件之前没做过的事：**拿真实数据，去质疑每一个结论。**

两天下来，发现的问题比写测试时抓到的所有 bug 加起来都多，而且性质完全不同。

---

## Bug 1：一键安装必然失败

最基础的一行承诺：

```bash
curl -fsSL https://raw.githubusercontent.com/Lishoulan/mcd-valor/main/install.sh | bash
```

我从来没跑过它。直到有一天我去查，才发现：

```bash
$ gh api repos/Lishoulan/mcd-valor/branches
  gh-pages
  master
```

**仓库里没有 `main` 分支。**

而这条命令在 install.sh、install.ps1、README、演示页里**一共出现了 10 次**，全部写死 `main`。

也就是说：**任何人执行一键安装，都会 404。**

**而我的测试全绿。**

---

## Bug 2：我在推荐一个已经下架的商品

`value` 命令的逻辑很简单：拉积分商城商品，按「每 100 积分能换多少元」排序。

跑出来是这样的：

```
18.8元麦辣鸡腿汉堡两件套   50积分   ¥18.8    ¥37.6/100分
✓ 最划算：18.8元麦辣鸡腿汉堡两件套
```

数字很漂亮。我顺手调了一下商品详情接口验证：

```json
{"success": false, "code": 610403, "message": "商品已下架"}
```

**它在推荐一个换不了的东西。**

而三个「看起来能判断下架」的字段，**全都不可靠**：

| 字段 | 实际情况 |
| --- | --- |
| `status` | **恒为 2**，零区分度 |
| `downTime` | 派对类是**未来日期**（2027-12-31），不能判 |
| 过滤 `spuId` 后 | 50 件全返回，**19 件其实已下架** |

唯一权威判据是商品详情接口。逐个核验后发现：**性价比前 12 名里 8 个已下架，包括原来的前 3 名。**

剔除之后，真实的最优汇率是：

```
¥37.6  →  ¥13.8     （降 63%）
```

**我把 README 里那个数字改了。** 虽然改完之后"标题党素材少了一半"。

---

## Bug 3：我给了一个从未验证过的建议

`redeem` 命令遇到门店用不了的券，原来的输出是：

> 试试外送场景或换一家门店

看起来很负责任。但我去看了代码——**它从来没查过外送场景，也从没验证过换一家门店有没有用。**

我实测查了 6 家门店（收藏店 3 家 + 按位置搜的 3 家），那些券**在任何一家的券池里都不存在**。

**「换一家门店」这个建议本身就是误导。** 用户到了门口才发现用不了。

后来加了外送核验。这里踩到的坑：

- `beType=2/5/6` 时**必传 `beCode`**，否则报 `600048`
- 而 `beCode` **只在 `beType=5`（得来速）的门店里有**，收藏门店返回的对象里根本没这个字段
- 取不到 `beCode` 时，工具现在会老实标「未核验」，**不假装查过**

## Bug 4：我测了"有数据"，没测"没数据"

我的账户有积分、有券、有门店。所有测试都在这个前提下跑。

**但新用户装上工具的第一天，是空账户。**

我写了 `tools/test_empty_account.py`：把所有接口替换成空返回，黑盒跑 8 个命令。结果全部优雅降级——**这是好消息**。

但更值得说的是：**这条路径我之前一次都没走过。**

---

## Bug 5：文档里的命令跑不通

我把文档变成测试：从 9 个文档里抽出所有 `python -m butler ...` 示例，逐条真的执行。

```bash
$ python tools/test_doc_commands.py
文档里出现的命令共 18 条
✗ butler stores 地铁站 --dt      ← 少了 --city
```

`--dt`（搜得来速）必须配 `--city`，README 漏了。照着抄会报：

```
600050 收藏餐厅列表为空，请您提供城市+关键词进行搜索
```

**这个报错会把人引向"接口有问题"，想不到是自己少写了参数。**

---

## 这 5 个 bug 的共同点

回头看，它们不是"代码写错了"。代码逻辑都对，**是结论错了**：

| Bug | 代码做了什么 | 实际发生了什么 |
| --- | --- | --- |
| 安装 | 拼了下载 URL | 指向不存在的分支 |
| 下架 | 按性价比排序 | 排序结果包含换不了的商品 |
| 外送 | 给了一条出路 | 那条路从没被验证 |
| 空账户 | 正常渲染 | 从没在空数据下跑过 |
| 文档 | 写了一行命令 | 那行命令少个参数 |

（上面这张表如果发知乎，记得手动转成列表——知乎会把 Markdown 表格压成一坨。见文末的发布说明。）

**它们的返回值全部正常，测试全绿。**

---

## 所以"测试通过"到底保证了什么

保证的是：**在你想到的那些输入下，函数行为符合预期。**

它保证不了：

- 你拼的 URL 指向一个不存在的东西
- 上游数据里混着你没预料到的状态（下架商品）
- 用户走的是一条你从没执行过的路径
- 文档里的示例少了一个参数

这四件事有个共同名字：**它们不在你的测试输入空间里。**

## 一个可操作的标准

后来我给自己定了个问题，逐条审视 11 个命令：

> **「如果没人投票、没人评分，你还会用它吗？」」

这个问题挖出来的东西，比任何功能清单都多。因为它逼你回答的不是"功能全不全"，而是**"这东西对真人有没有用"**。

顺着它，我又加了三个测试：

```bash
python tools/test_doc_commands.py    # 文档里的命令逐条实跑（18 条）
python tools/test_doc_links.py       # 文档相对链接（16 条）
python tools/test_empty_account.py   # 空账户降级（8 个命令）
python tools/test_windows.ps1        # Windows 路径（16 条，PowerShell 5.1）
```

`test_doc_commands.py` 当场就抓出了上面那个 `--city` 缺失。

## 过程中我也给自己埋了雷

诚实交代，这两天我自己引入的 bug 不少：

**① 改完只测一半。** 修 `--endpoint` 参数位置时，只测了"参数放子命令后"，发现能用了就收工。结果"参数放前面"被弄坏了。是后来测四种组合才发现的。

**② 文档里写了个真的坏命令。** README 里那段"测试抓出过 --dt 少 --city"，为了举例把坏命令原样写了进去。于是 `test_doc_commands.py` 每次都报它失败——我第一反应是"又出新 bug 了"。

**③ Write 工具写的 `.ps1` 不带 BOM。** PowerShell 5.1 按 GBK 读 UTF-8，中文注释全乱码，脚本语法直接崩。讽刺的是 `install.ps1` 上我早就小心过这件事。

**④ 把假 bug 当成真的。** PowerShell 捕获 stdout 时中文显示成 `鈹?`，我以为是产品编码 bug。实测直接输出到终端完全正常——是 PowerShell 5.1 捕获管道的老问题。

## 几条具体的经验

**① 安装脚本是最该实测的东西，也最容易被跳过。**

因为它"太简单了"，简单到你觉得不需要测。而它是用户接触产品的第一步。

**② 上游返回的每个字段，先问"它能区分什么"。**

`status` 恒为 2、`downTime` 对未来日期无效——这类字段看着能判断，其实不能。**不能识别的字段比没有字段更危险**，因为它会让你以为自己在验证。

**③ 给不出路的建议，不如不给。**

"试试换一家门店"听起来负责，但如果从没验证过，它比沉默更糟——用户会为此跑一趟。

**④ 空状态是独立的一条路径。**

有数据时跑通，不代表没数据时跑通。这是两套输入空间。

**⑤ 文档是代码的一部分。**

文档里的命令跑不通，文档就是 bug。我把它变成了测试，然后当场抓到一个。

---

## 最后

那 5 个 bug，**一个都不是单元测试能发现的。**

它们需要的是：真实接口、真实数据、以及**质疑每一个结论**的耐心。

写测试当然有价值。但如果你只跑自己写的测试，你验证的只是**自己的想象**。
