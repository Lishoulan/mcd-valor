# 我给麦当劳的积分工具挑了个刺，结果发现两个自己写的 bug

> 起因很简单：我想知道我的麦当劳积分到底能换什么，写了个命令行工具。
> 写完顺手测了一下，发现自己在**推荐一个已经下架的商品**。
> 于是把 11 个命令全查了一遍。

## 先说结论

这个项目用麦当劳官方 MCP 做了 11 个命令，零第三方依赖。
但真正让我觉得有意思的不是功能，而是**我为了验证它，挖出来的三个反直觉结论**——
其中一个是我自己的 bug。

在线演示：https://lishoulan.github.io/mcd-valor/
代码：https://github.com/Lishoulan/mcd-valor

---

## 一、积分商城会把已下架的商品一起返回

我最初写的 `value` 命令，逻辑很简单：拉 `mall-points-products`，按「每100 积分能换多少元」排序。

跑出来是这样的：

```
★ 兑换性价比排行· 每 100 积分能换多少元
  18.8元麦辣鸡腿汉堡两件套50   ¥18.8    ¥37.6  可换 31 份
  ✓ 最划算：18.8元麦辣鸡腿汉堡两件套
```

数字很漂亮。但我顺手点进 `mall-product-detail` 验了一下：

```json
{"success": false, "code": 610403, "message": "商品已下架"}
```

**它在推荐一个换不了的东西。**

我以为 `status` 字段能判断，查了发现**恒为 2**，区分不出来。
又看 `downTime`，发现派对类商品的 `downTime` 是**未来日期**（比如 2027-12-31），也不能判。

于是我逐个调`mall-product-detail` 核验，实测：

- 商城 50 件商品里，**19 件已下架**
- 性价比**前 12 名里8 个已下架**，包括原来的前 3 名

剔掉之后，真实的最优汇率是：

```
已剔除 13 件已下架商品（经 mall-product-detail 逐个核实，返回 610403）

  6.9元可乐麦炫酷50   ¥6.9    ¥13.8  可换 31 份
  ✓ 最划算：6.9元可乐麦炫酷
```

**每 100 积分值 ¥37.6 → ¥13.8，降了 63%。**

我把这个数字从README 里改掉了。虽然改完之后标题党素材少了一半，但用户是照着这个数字去兑换的——
**给一个换不了的数字，比不给数字更糟。**

## 二、「有券要过期」这个提醒，本身是没用的

第二个问题更有意思。

`redeem` 命令原本对不可用的券会建议：

> 试试外送场景或换一家门店

看起来很负责任。但我去看了代码，**它从来没查过外送场景**，也**从没验证过换一家门店有没有用**。

我实测查了 6 家门店（收藏店 3 家 + 用 `searchType=2` 按位置搜的 3 家），结果那些券**在任何一家的券池里都不存在**。

**「换一家门店」这个建议本身就是误导**——用户到了门口才发现用不了。

所以我加了外送核验。这里踩了几个 MCP 的坑：

- `orderType=2` + `beType=2` 时**必传 `beCode`**，否则服务端报 `600048`
- `beCode` **只在 `beType=5`（得来速）搜到的门店里才有**，收藏门店（`searchType=1`）返回的对象里**根本没有这个字段**
- `beType=5` + `searchType=1` 会报 `600050`「收藏餐厅列表为空」，必须带城市 + 关键词

改完之后（以下是某一天的输出，券数每天在变）：

```
外送场景核对中…
✗ 外送也不可用： 人气麦旋风买一送一
✗ 外送也不可用： 火腿扒堡早餐两件套

✗ 4 张券确认救不回：
· 人气麦旋风买一送一（2026-10-11 到期）
    到店 3 家门店不支持，外送也不在券池——这张券这次用不了了。
```

顺便说一下，**取不到 `beCode` 时它会老实标「未核验」，不假装查过**。
工具知道自己不知道什么，这比装懂重要。

## 三、抽奖抽的券不在卡包里

这个不是我发现的 bug，是官方数据结构本身的问题。

`query-my-coupons`（卡包券）和 `query-my-prizes`（抽奖奖品）是**两个完全独立的数据源**。
抽奖抽到的券**只在后者里**。

所以任何只查卡包的「临期提醒」工具——**结构上就看不到它们**。

我的账户 19 个奖品里 3 个已失效，全部是抽中的优惠券，可用期只有 6 天却没人用掉。
19 个里有 16 个是门票，所以工具现在会把券和门票**分组显示**——不然真正的券会被淹掉。

## 四、顺带一个：官方字段自己就不自洽

`account` 命令输出里同时有这两行：

```
本月将过期0 分（本月无积分过期）
⚠ 你已经白白过期了 2902.9 分
```

用户看到会懵。我去查了原始返回：

```
累计 6345.4 − 可用 1583.5 − 已用 1595.0 = 3166.9
但 expiredPoint = 2902.9← 差 264 分
```

官方没解释这264 分是什么。可能是活动结算、可能是口径不同、也可能是别的。

我的处理是：**把这个差额摆出来，然后说「我不知道这是什么」。**

```
官方字段之间也不自洽：累计 6345.4 − 可用 1583.5 − 已用 1595.0 = 3166.9，
与 expiredPoint 差 264.0 分。本工具按官方 expiredPoint 显示，不替你猜这差额是什么。
```

## 这些 bug 单元测试测不出来

这是我想说的最重要的一点。

上面两个 bug，**函数返回值完全正常，当时手写的回归测试全绿**。

因为它们的本质不是「代码写错了」，而是**「结论是错的」**：
返回值没错，但它建议你去做一件做不到的事。

这类 bug 只有一种测法：**拿真实数据跑一遍，然后质疑每一个结论**。

于是我给自己定了个标准，逐条审视 11 个命令：

> **「如果没人投票、没人评分，你还会用它吗？」**

这个问题挖出来的东西，比任何功能清单都多。

## 顺带几条 MCP 的坑（可能对你有用）

这几条文档里都没写，我是实测踩出来的：

**① 券 × 门店查不到，不一定是请求失败**

门店**不存在或不支持时返回的是空数组 `[]`，而不是报错**。
空数组是合法的「不可用」信号—— 我见过不少工具在这里当成异常处理。

**② `searchType=1` 搜不到别的店**

`searchType=1`（默认）**只搜收藏门店，会忽略 `keyword` 参数**。
所以你搜任何词都返回同一批店。要搜别的店得用 `searchType=2` 并且带上城市。

**③ 外送场景报 `600048`**

`beType` 为 2/5/6 时**必传 `beCode`**，否则服务端直接拒。
而 `beCode` **只在 `beType=5`（得来速）搜到的门店里才有**，收藏门店返回的对象里根本没这个字段。

**④ `status` 判断不了商品下架**

商城商品的 `status` **恒为 2**，没有任何区分度。
`downTime` 也不可靠—— 派对类商品的 `downTime` 是未来日期。
只有 `mall-product-detail` 返回 `610403` 才是权威判据。

**⑤ 字段名拼错了：不是 `currentMonthExpirePoint`**

是 `currentMouthExpirePoint` —— 服务端把 `Month` 拼成了 `Mouth`。
按直觉写 `currentMonth...` 会**取到空值而不报错**，静默失效。

**⑥ 抽奖期望值算不了**

`query-lottery-info` 的奖品列表里**没有任何概率字段**。
概率未知时算期望值就是编造 —— 只能给成本与奖池，让用户自己决定。

## 一点感想

做这个项目最大的收获不是那11 个命令，而是意识到一件事：

**「提醒你该处理了」是最容易做、也最没用的一类功能。**

我做的第一版`redeem` 就是典型——它能查出「有几张券要过期」，但用户拿着这个告警**依然不知道该干什么**。

真正有用的答案是「其中 4 张在你常去的店用不了，今天该去的是这 2 家」，甚至「这 4 张连外卖都救不回来，别白跑了」。

**前者需要三个 MCP 接口交叉验证，后者需要承认工具自己也不知道。**

这两个都不难，难的是忍住不去编一个好看的结论。
